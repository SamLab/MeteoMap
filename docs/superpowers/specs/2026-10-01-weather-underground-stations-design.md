# Станции Weather Underground восьмым и девятым датчиками

Дата: 2026-10-01
Статус: на согласовании

## Задача

Добавить две любительские станции Weather Underground (PWS) в сеть датчиков:
Ананьино (15.3 км к югу от центра) и Заволжское (24.3 км к северу). Обе
равноправны с существующими: входят в `mean(mean(станции))` без поправочного
коэффициента. Решение о включении в среднее принято пользователем осознанно.

Берём только температуру. Ветер, влажность и давление с WU не берём: сеть
измеряет только `temperature_2m`, и `SENSOR_PARAMS` намеренно ограничен ею
(см. `2026-09-28-sensors-temperature-only-design.md`).

## Источник

Weather Underground Personal Weather Station API, тот же веб-ключ, что вшит в
сайт wunderground.com. Ключ публичный, не является нашим секретом.

```
https://api.weather.com/v2/pws/observations/current
    ?stationId=<ID>&format=json&units=m&apiKey=<KEY>
```

`units=m` даёт температуру в Цельсиях, ветер в м/с. Заголовок `User-Agent`
обязателен, `Referer` не нужен.

Проверено на живых данных 2026-10-01 (20:30–20:44 UTC):

| Свойство | Ананьино | Заволжское |
|---|---|---|
| `stationId` (в конфиг) | `I90583615` | `IZAVOLZH3` |
| Координаты | `57.48765 / 39.94122` | `57.81076 / 40.06904` |
| Расстояние от центра | 15.3 км | 24.3 км |
| `metric.temp` | +5 °C | +4 °C |
| `humidity` | 82% | 91% |
| `obsTimeUtc` | `2026-10-01T20:43:01Z` | `2026-10-01T20:44:12Z` |
| `qcStatus` | -1 | -1 |

Температуры правдоподобны и совпадают с аэропортовым METAR за тот же час
(+5 °C). Обе станции отчитываются свежими (в пределах минуты).

### Формат ответа

```json
{"observations": [{
  "stationID": "IZAVOLZH3",
  "obsTimeUtc": "2026-10-01T20:44:12Z",
  "humidity": 91,
  "qcStatus": -1,
  "metric": {"temp": 4, "windSpeed": 0, "pressure": 1016.26, "...": "..."}
}]}
```

Значение — `observations[0].metric.temp`, метка наблюдения —
`observations[0].obsTimeUtc` (ISO `…Z`, тот же формат, что у METAR).

### Почему не другие сети

Проверены 2026-10-01 по покрытию Ярославля и доступности без ключа:

- **Народный мониторинг** — уже подключён отдельно (`tools/collect_narodmon.py`,
  untracked). Это другая задача.
- **openSenseMap** — keyless, но в районе Ярославля станций нет.
- **Sensor.Community** — только пыль (PM), в радиусе 10 км ни одной станции.
- **Windy.com** — станционный эндпоинт `stations.windy.com/stations` закрыт
  (POST/CSRF, отдаёт 403/500), публичного API нет. Станция аэропорта там — тот
  же METAR.
- **windy.app** — станция `MADIS_UUDL` байт-в-байт повторяет METAR Туношны по
  температуре, скорости и направлению ветра каждые 30 минут. Отдельных данных
  не даёт.
- **WeatherCloud, AWEKAS, WeatherLink (Davis), Ecowitt, Ambient, Netatmo** —
  требуют ключ/регистрацию, покрытие по Ярославлю практически нулевое.

## Конфигурация

`tools/stations.json`, новые станции (после `uudl`):

```json
{
  "id": "wu-ananyino",
  "name": "Ананьино",
  "lat": 57.48765,
  "lon": 39.94122,
  "source": "wu",
  "max_age_s": 1800,
  "sensors": { "temperature_2m": "I90583615" }
},
{
  "id": "wu-zavolzhskoe",
  "name": "Заволжское",
  "lat": 57.81076,
  "lon": 40.06904,
  "source": "wu",
  "max_age_s": 1800,
  "sensors": { "temperature_2m": "IZAVOLZH3" }
}
```

Координаты настоящие, взяты из ответа `v3/location/near`.

`source: "wu"` — четвёртое значение `VALID_SOURCES` рядом с `mqtt`, `http`,
`metar`.

`max_age_s: 1800` — WU обновляется примерно раз в 5 минут; порог в 3× периода
даёт тот же запас, что 2400 с у METAR (2× от 30 минут), и переживает пропуск
циклов без ложного протухания. Общий порог 900 с трогать не нужно: у `yartemp`
требование к свежести не ослабляется.

## Изменения в `tools/collect_sensors.py`

### 1. Четвёртый транспорт

`VALID_SOURCES = ('mqtt', 'http', 'metar', 'wu')`.

`http_stations()` (сейчас `source in ('http', 'metar')`, строка 123) начинает
брать и `wu`: все три источника опрашиваются по сети.

`station_fetcher()` (строка 307) по `source == 'wu'` возвращает `wu_fetcher`.

`collect()` (строка 677) уже отбирает только `mqtt` для подписки, поэтому
станции WU в брокер не попадут без изменений.

### 2. Адаптер `fetch_wu(url, timeout_s, now, session)`

По образцу `fetch_metar` (строка 216), с той же гарантией: **не бросает
исключений ни при каком ответе**.

- GET с заголовком `User-Agent`, без `Referer`.
- Ответ — JSON-объект с полем `observations` (не массив верхнего уровня, как у
  METAR). Берётся первая запись.
- Значение — `metric.temp`; отсутствие `metric`, `temp` = `null`, `bool`,
  нечисло или выход за `SENSOR_PARAMS` → `(None, None)`.
- Метка — `obsTimeUtc`, разбирается тем же парсером ISO-8601, что и METAR
  (`parse_metar_report_time`, строка 194). Парсер уже умеет `Z`, миллисекунды и
  смещение; переиспользуем его. Историческое «metar» в имени не мешает: это
  общий разбор `reportTime`/`obsTimeUtc`.
- Сверка `observations[0].stationID` с запрошенным id — как `expect_icao` у
  METAR (строка 263). Опечатка в конфиге тогда молчит по понятной причине, а не
  выдаёт чужую станцию за нашу.
- Значение возвращается строкой, как у `fetch_yartemp`/`fetch_metar`, чтобы
  `build_snapshot` оставался единым.

### 3. Обёртка `wu_fetcher(station_id, ...)`

В конфиге лежит короткий `stationId` (`I90583615`), он же служит ключом словаря
`received`. Сам по себе это не адрес, поэтому URL собирает `wu_fetcher` — ровно
так же, как `metar_fetcher` (строка 293) разворачивает `UUDL` в адрес NOAA. Иначе
`requests` на токене упал бы с `MissingSchema`, адаптер проглотил бы исключение,
и станция молчала бы каждый прогон, не оставив следов.

Адрес и публичный ключ — модульные константы:

```python
WU_API_KEY = '6532d6454b8aa370768e63d6ba5a832e'  # публичный веб-ключ wunderground.com
WU_ENDPOINT = ('https://api.weather.com/v2/pws/observations/current'
               '?stationId=%s&format=json&units=m&apiKey=' + WU_API_KEY)
```

### 4. Свежесть

Общий механизм `collect_http` (строка 339) применяет `station_max_age_s(st)`,
то есть 1800 с для обеих станций. Метка из будущего прижимается к `now`
(строки 337-338). Метка прихода — `obsTimeUtc`, время наблюдения, а не время
запроса: `age_s` на сайте показывает возраст показания.

### 5. Валидация

`load_stations()` принимает `source: "wu"` (через общий `VALID_SOURCES`).
Дополнительных полей не требуется.

## Данные и среднее

Поток ниже `collect()` не меняется: `build_snapshot → record_history → снимок →
meteo.py → сайт`. Замер кладётся в бакет часа наблюдения (как у METAR), потому
что `build_snapshot` пишет `value_hours[param] = moscow_hour_key(ts)` по метке из
`seen`, а `record_history` читает именно `value_hours`.

Обе станции входят в `models['sensors'].temperature_2m` наравне с остальными,
как аэропорт (19 км). Следствие, принятое пользователем: среднее по городу
немного сдвинется — Ананьино на юге и Заволжское за Волгой дают более широкий
охват, чем компактная городская сеть и аэропорт.

### Известные ограничения

- **Любительские станции.** Могут пропадать или отдавать мусор (проверенная
  соседняя `ILEVOBER3` показывала -40 °C). Отсечка `null`, нечисла и
  `[-50, 50]` закрывает грубые выбросы; станция без данных молча исключается из
  среднего, а не считается нулём.
- **`qcStatus` не фильтруем.** У обеих станций он `-1` и как признак качества
  бесполезен; использовать его значило бы выбросить обе станции целиком.
- **Дубликаты.** WU обновляется чаще, чем идёт CI, поэтому один замер может
  попасть в бакет несколько раз. Ограничение то же, что у METAR, и так же
  фиксируется тестом: `_sensor_hour_value` считает `mean` списка замеров, при
  равномерном покрытии копий среднее не искажается.
- **Публичный ключ.** Ключ общий с веб-сайтом wunderground.com и может быть
  ограничен по частоте. Расход — 2 запроса на прогон; частоту CI не меняем.

## Что не меняется

`meteo.py` целиком: конвейер ниже `collect()` транспортонезависим и работает
через словари `received`/`seen`. Веса, консенсус, верификация, виджеты
(`meteo.html`, `meteow.html`) не трогаются. Переиспользуется существующий
механизм `max_age_s`, введённый для METAR.
