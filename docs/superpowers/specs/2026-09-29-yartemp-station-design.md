# Датчик yartemp.com как пятая станция Ярославля

**Статус: утверждён владельцем** (решение владельца 2026-09-29: «добавить 5-й
станцией в Ярославль», «брать только температуру», «иди до деплоя не спрашивая»)

Предыдущая работа: `docs/superpowers/specs/2026-09-29-tsedenevo-night-minimum-design.md`.

## Задача

Добавить в среднее и минимум по датчикам пятую станцию — датчик
`yartemp.com`, единственный независимый от MQTT-брокера источник. Берём
**только температуру**; остальные поля ответа игнорируются.

## Что представляет собой источник

`yartemp.com` — не сеть станций, а один датчик в Ярославле. Данные лежат в
недокументированном endpoint'е:

```
GET https://yartemp.com/webdata/?<unix_millis>
→ "8.090;1790708310;-0.146;3.193;9.819;..."
```

Ответ — одна строка, поля разделены `;`, без авторизации и без JSON:

| Поле | Смысл | Используем |
|---|---|---|
| `[0]` | текущая температура, °C | **да** |
| `[1]` | Unix-время **самого замера**, секунды | **да**, как метка прихода |
| `[2]` | изменение за час | нет |
| `[4]` | среднее за 24 ч | нет |
| `[7]`/`[8]` | мин/макс за сутки | нет |
| `[9]`/`[10]` | восход/заход | нет (свои, от open-meteo) |
| `[17]` | давление | нет |
| прочие | солнце, луна, свет | нет |

Проверено вручную 29.09.2026: HTTP 200, 125 байт, поле `[1]` отстаёт от
системных часов на 25 с — то есть это метка замера, а не время отдачи страницы.

## Решения владельца

1. Станция входит в обычное среднее и минимум по Ярославлю (и, следовательно,
   в ночной минимум Цеденево — он использует те же станции).
2. Только температура.
3. Не задавать уточняющих вопросов, довести до деплоя.

### Решение, принятое за владельца: координаты

Станция **не публикует координаты**. FAQ говорит только «в Ярославле» и
предупреждает, что в разных районах города температура отличается на 1-2 °C.
`load_stations` требует `lat`/`lon`, поэтому берём координаты существующей
станции `east` (57.62, 39.92) — это текущий центр Ярославля.

Обоснование: координаты в этом проекте **не влияют ни на что** при сборе и
не публикуются в снимке для отображения — они нужны только как обязательное
поле конфига. Выдумывать точность до метра значило бы записать в репозиторий
ложную точность. Центр города — честная величина с честной точностью.

## Правовой статус

FAQ yartemp, раздел «А можно использовать эти данные на другом сайте?»:

> Да, можно, но если вы собираетесь их использовать на регулярной основе, то
> лучше написать письмо автору. Также, если вы публикуете где-либо
> температурные графики, то обязательно проставьте ссылки на оригинальный
> сайт: https://yartemp.com/

Итого: использование **разрешено**, регулярное использование автор
**просит** согласовать письмом, при публикации графиков нужна ссылка на
оригинал. Мы не публикуем графики yartemp, но показываем его данные рядом с
данными наших станций, поэтому ссылка на источник добавляется в интерфейс.

## Архитектура

Ключевое наблюдение: весь конвейер ниже `collect()` — `build_snapshot()`,
`record_history()`, раскладка по часам, `_sensor_hour_value()` в `meteo.py` —
**уже независим от транспорта**. Он принимает `received` (строковый ключ →
сырой payload) и `seen` (ключ → время прихода). MQTT — лишь один способ
наполнить эти словари.

Значит HTTP-станция не требует ни одной правки в `meteo.py`, ни в
`build_snapshot`, ни в `record_history`, ни в истории бакетов. Это сводит
изменение к двум файлам: конфиг и адаптер.

```
                    ┌─ mqtt: collect() ──┐
stations.json ──────┤                    ├── received{} / seen{} ── build_snapshot ── sensors.json
                    └─ http: fetch_yartemp() ┘                                            │
                                                                                          ▼
                                                                        record_history ── sensors_history.json
                                                                                              │
                                                                                              ▼
                                                                                     meteo.py (без правок)
```

### `sensors` в конфиге: URL вместо топика

У MQTT-станции `sensors: {"temperature_2m": "<топик>"}`. Для yartemp в этом
поле лежит URL. Ключ в `received`/`seen` — **этот же URL**, поэтому
`build_snapshot` не различает источники и не меняется вовсе.

Новая станция:

```json
{
  "id": "yartemp",
  "name": "Ярославль, yartemp.com",
  "lat": 57.62,
  "lon": 39.92,
  "source": "http",
  "sensors": {
    "temperature_2m": "https://yartemp.com/webdata/"
  }
}
```

`"source": "http"` — явный признак, что поле `sensors` содержит не топик.
Отсутствие поля означает `mqtt`, поэтому конфиг существующих станций не меняется
и обратная совместимость сохраняется.

### `fetch_yartemp()` — единственная новая функция

```python
def fetch_yartemp(url, timeout_s=20, session=None):
    """Опрашивает HTTP-станцию. Возвращает (payload, reading_ts) или (None, None)."""
```

Контракт:

- делает **один** GET, подставляя cache-busting query (`?` + unix_millis), как
  это делает сам сайт;
- парсит строку по `;`, берёт **только** `[0]` и `[1]`;
- `[1]` — метка **замера**, и она же кладётся в `seen`: `age_s` на сайте
  покажет реальный возраст показания, а не возраст нашего запроса;
- **не бросает исключений**: сетевой сбой, не-HTML ответ, пустое поле, мусор
  вместо числа — это «нет данных», а не падение прогона. Публикация
  `sensors_history.json` не должна зависеть от чужого сайта.

Возвращаемое значение подставляется в словари как обычное MQTT-сообщение:

```python
if payload is not None:
    received[url] = payload      # "8.090"
    seen[url] = reading_ts        # 1790708310.0
```

### Свежесть

`validate()` отбрасывает значение вне `-50..50`, но не смотрит на возраст.
Для HTTP-источника это опасно: зависший сайт отдаёт последнее показание
неограниченно долго, и оно молча попадёт в среднее как живое.

Поэтому протухшая HTTP-инъекция **не делается вовсе**. Порог свежести живёт в
адаптере, а не в `build_snapshot`:

```python
HTTP_MAX_AGE_S = 900   # 15 минут: три подряд пропущенных обновления

payload, reading_ts = fetch_yartemp(url, now=now)
if payload is not None and now - reading_ts <= HTTP_MAX_AGE_S:
    received[url] = payload
    seen[url] = reading_ts
# иначе в словари не пишем → станция online: false → в среднее не попала
```

Проверка **до** записи в `received` — единственное место, где она возможна без
правки `build_snapshot`: этот код ничего не знает ни про HTTP, ни про
`stations.json`, он видит только `received`/`seen`. Так «среднее четырёх
станций, где четвёртая — вчерашняя» на сайте невозможно, и `build_snapshot`
остаётся нетронутым.

`age_s` считается корректно и без отдельной правки: `build_snapshot` берёт
`ref = last_ts` из `seen`, а мы кладём туда метку **замера**, поэтому возраст
показывает свежесть показания, а не возраст нашего запроса.

Это тот же принцип, что и с retained-сообщениями MQTT: «не услышанное
помечается offline, поэтому протухшие значения не выдаются за живые».

### Отказоустойчивость и politeness

- Один GET за прогон, цикл 10 минут — это ~144 запроса в сутки. Нагрузка
  ничтожна для сайта, который сам обновляет страницу каждые 5 секунд.
- `Referer: https://yartemp.com/` — тот же, что шлёт сам сайт.
- Поле `Referer` в `sensors.json` не попадает.
- Отдельный ретрай не делаем: следующий прогон через 10 минут и есть ретрай.

## Тестирование

- `fetch_yartemp` на настоящем ответе: берёт `[0]` как значение, `[1]` как
  время замера.
- Мусор вместо числа, пустой ответ, HTTP-ошибка, не-`;`-строка → `(None, None)`,
  **без исключения**; станция в снимке `online: false`.
- `load_stations` принимает `source: "http"` и URL в `sensors`; MQTT-станции
  без поля `source` остаются валидными.
- `build_snapshot` получает инъекцию в `received`/`seen` и **ничем не отличается**
  от MQTT-пути: станция online, `age_s` = возраст замера, значение в `values`.
- Замер старше 900 с → станция offline, в среднем не участвует, в
  `sensor_station_counts` не попадает.
- `tools/stations.json`: пять станций, ровно одна с `source: "http"`, у всех
  только `temperature_2m`.
- Полный набор тестов зелёный; `meteo.py` пересобирает сайт, в payload
  Ярославля и Цеденево `sensor_station_counts` в новых часах равен 5.

## Чего НЕ делаем

- Не берём давление, влажность, ветер, осадки — их yartemp всё равно не
  отдаёт в нужном нам виде, а влажность/давление у датчиков уже исключены
  решением от 28.09.
- Не запрашиваем у автора письменного разрешения автоматически и не публикуем
  графики yartemp.
- Не меняем `window_s` (350), расписание `*/10`, `history_days` (30).
- Не трогаем `meteo.py` и `template.html`: транспорт живёт только в коллекторе.
- Не выдумываем координаты точнее центра города.
- Не удаляем накопленную историю: старые бакеты остаются с четырьмя станциями,
  новые — с пятью, среднее само переедет.

## Риски

**Зависимость от чужого сайта без гарантий.** FAQ прямо пишет, что
«круглосуточная работоспособность сайта не гарантируется». Отсюда порог
свежести 900 с: три подряд пропущенных обновления — и станция молча выпадает
из среднего, сайт этого не сломает.

**Смена формата.** Endpoint недокументированный. `fetch_yartemp` падает в
`None` при любом несоответствии формата, а не в исключение: худший исход —
станция перестаёт давать значение, а не роняет публикацию.

**Незапрошенные изменения в чужом endpoint'е.** `/gb/` для писем. Мы туда не
пишем автоматически.
