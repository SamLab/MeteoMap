# METAR аэропорта Ярославля шестым датчиком

Дата: 2026-09-30
Статус: утверждён

## Задача

Добавить METAR аэропорта Ярославля (Туношна) как шестую станцию сети датчиков.
Станция равноправна с пятью существующими: входит в `mean(mean(станции))` без
поправочного коэффициента.

## Источник

NOAA Aviation Weather Center:

```
https://aviationweather.gov/api/data/metar?format=json&ids=UUDL&hours=1
```

Открыт, ключа не требует, отдаёт JSON. Домен правительства США, поэтому
указание авторства не обязательно. Ответ требует заголовка `User-Agent`.

Проверено на живых данных 2026-09-30:

| Свойство | Значение |
|---|---|
| `icaoId` | `UUDL` |
| `name` | `Yaroslav/Tunoshna Arpt, YA, RU` |
| Координаты | `57.561 / 40.157`, высота 88 м |
| IATA | `IAR` |
| Расстояние от центра Ярославля | 19 км |
| Частота | ровно 30 минут |
| Объём за сутки | 48 сводок, все интервалы 30 мин |
| Поля | `temp`, `dewp`, `wspd`, `wdir`, `altim`, `visib`, `clouds` |

### Почему не другие источники

Проверены и отброшены:

- **Ogimet, metartaf.ru, avia.meteonovosti.ru** — отдают байт-в-байт ту же
  сводку. Это перепечатка одного зарубежного фида, поэтому парсить HTML
  вместо JSON незачем.
- **flightradar24** — SPA, данные в JSON-эндпоинтах; в HTML только мета-теги.
- **windy.com** — отдаёт 77 символов, остальное грузится скриптом.
- **metar-taf.com** — HTTP 403 на автоматические запросы.

### Ключевой код

`UUDL`, а не `ULLK`. `ULLK` в каталоге NOAA отсутствует и не отдаёт METAR ни за
3, ни за 24, ни за 168 часов. Первая версия этой работы искала неверный код и
пришла к ложному выводу, что Туношна молчит. Правильный код подтверждён
каталогом NOAA: `UUDL` → `Yaroslav/Tunoshna`, 19 км от центра.

## Известный эффект, сознательно не документированный

Аэропорт на открытом поле в 19 км от города. Ночью он систематически холоднее
городских станций — замерено по часам 2026-09-30:

| Час (МСК) | Аэропорт | Сеть | Расхождение |
|---|---|---|---|
| 07:00 | 4-5° | 8.2° | -3.2...-4.2° |
| 08:00 | 7-8° | 9.9° | -1.9...-2.9° |
| 09:00 | 9-11° | 12.0° | -1.0...-3.0° |
| 10:00 | 12-13° | 13.2° | -0.2...-1.2° |
| 11:00 | 14-15° | 14.8° | -0.8...+0.2° |
| 12:00 | 16° | 15.0° | +1.0° |

Это физика, а не сбой: ночное выхолаживание открытого поля сильнее городского.
Смещение признано, решение оставить в среднем принято пользователем осознанно
после того, как расхождение было показано.

**Решение: в справке сайта не упоминается.** Пользователь решил не объяснять
расхождение. Эффект фиксируется здесь, чтобы он не выглядел упущением при
следующем разборе расхождений.

## Конфигурация

`tools/stations.json`, шестая станция:

```json
{
  "id": "uudl",
  "name": "Ярославль, аэропорт (METAR)",
  "lat": 57.561,
  "lon": 40.157,
  "source": "metar",
  "max_age_s": 2400,
  "sensors": { "temperature_2m": "UUDL" }
}
```

Координаты настоящие, взяты из каталога NOAA. У `yartemp` координаты выдуманы
(взяты у другой станции), потому что сайт их не публикует; здесь такой
необходимости нет.

`source: "metar"` — третье значение `VALID_SOURCES` рядом с `mqtt` и `http`.

## Изменения в `tools/collect_sensors.py`

### 1. Третий транспорт

`VALID_SOURCES = ('mqtt', 'http', 'metar')`.

`http_stations()` берёт и `http`, и `metar` — оба опрашиваются по сети.
`collect_http()` выбирает адаптер по `source`: `fetch_yartemp` для `http`,
`fetch_metar` для `metar`. Словари `received`/`seen` и весь код ниже остаются
без изменений.

### 2. Поле `max_age_s`

Новое необязательное поле в станции. Значение по умолчанию —
`HTTP_MAX_AGE_S` (900), поэтому `yartemp` не меняется ни на строчку.

Зачем: METAR обновляется раз в 30 минут, и при общем пороге 900 секунд он
протухал бы всегда, то есть не дал бы ни одного числа. Для METAR
принимается 2400 секунд — с запасом сверх периода.

Порог остаётся per-source, а не становится общим 2400: у yartemp не должно
ослабляться требование к свежести.

### 3. Адаптер `fetch_metar(url, timeout_s, now, session)`

По образцу `fetch_yartemp` (строки 108-161), с той же гарантией: **не бросает
исключений ни при каком ответе**.

- GET с заголовком `User-Agent`, без `Referer` — источник его не требует.
- Ответ — JSON-массив. Берётся первая запись, у неё `temp` и `reportTime`.
- `reportTime` разбирается в unix-время: формат `2026-09-30T09:30:00.000Z`
  содержит миллисекунды, которые не понимает `datetime.fromisoformat`, поэтому
  миллисекунды отбрасываются перед разбором.
- `temp` проверяется на число и на попадание в диапазон `SENSOR_PARAMS`.
- Значение возвращается строкой, как у `fetch_yartemp`, чтобы
  `build_snapshot` оставался единым.

### 4. Свежесть

`collect_http()` применяет порог станции:

```python
max_age_s = st.get('max_age_s', HTTP_MAX_AGE_S)
if now - reading_ts > max_age_s:
    continue
```

Метка прихода — `reportTime`, то есть время наблюдения, а не время нашего
запроса. Это делает `age_s` честным: показывает возраст именно показания.

### 5. Валидация

`load_stations()` принимает `source: "metar"`. Новое поле `max_age_s`
проверяется как положительное число, если присутствует.

## Данные

- Замер кладётся в бакет часа **наблюдения**, а не часа прогона. Работает это
  само по себе: `build_snapshot` (строка 240) пишет
  `value_hours[param] = moscow_hour_key(ts)`, где `ts` — время показания, а
  `record_history` (строка 411) читает именно `value_hours`, а `hour_key` года
  прогона использует только как запасной вариант. Для METAR в `seen` попадёт
  `reportTime`, поэтому новая логика не нужна.
- METAR наблюдает в :00 и :30 UTC, обе сводки попадают в один московский бакет
  часа — проверено на живых данных: 09:00Z и 09:30Z дают бакет `12:00`.

### Известное ограничение: дубликаты

METAR обновляется 2 раза в час, CI ходит 6 раз в час, поэтому одна и та же
сводка попадает в бакет примерно трижды. Среднее станции это переживает:
`_sensor_hour_value` считает `mean(список замеров станции)`, а при равномерном
покрытии копий среднее не искажается.

Если прогоны CI приходят неравномерно, баланс копий смещается. Смещение среднего
часа относительно идеала не может превысить половины разницы между двумя
наблюдениями, то есть ≤0.5°C при гранулярности METAR в 1°C. При нормальном
ходе CI (три прогона на сводку) смещение ≈0.1°C — это заметно меньше
гранулярности источника и на фоне суточного разброса не видно.

**Почему не чинить сейчас.** Дедупликация по значению сломала бы `yartemp`,
где повторы значений законны: станция может дважды подряд отдать 12.4, и это
два настоящих замера, а не копия одного. Различение требует хранения времени
наблюдения в бакете, что меняет формат истории и затрагивает оба её читателя.

Ограничение фиксируется тестом. Если фактическое смещение окажется заметным,
это отдельная задача с новым полем в формате бакета.

## Что не меняется

`meteo.py` целиком. Весь конвейер ниже `collect()` транспортонезависим: он
работает через словари `received`/`seen` и не знает, откуда пришли данные.

Проверено на истории: коммит `6a42e36` (добавление `yartemp` как
HTTP-станции) тронул `meteo.py` на 57 строк, но ни одна из них не изменила
арифметику — это `_sensor_station_ids` и проброс `station_ids` для ссылки на
источник. Сама `_sensor_hour_value`, которая и считает среднее, при смене
транспорта не менялась. Новая станция требует той же атрибуции, но её код
уже написан и менять нечего.

Не трогаем: веса, консенсус, верификацию, виджеты, `template.html` (кроме
справки), бэкфилл истории.

`template.html`, раздел «Датчики»:

- периодичность: уточнить, что METAR обновляется раз в 30 минут, остальные —

## Тесты

`tests/test_sensors.py`, по существующим блокам:

- `max_age_s`: значение по умолчанию 900; переопределение станции.
- METAR-станция не попадает в MQTT-подписку.
- `fetch_metar`: температура из JSON; пустой массив; HTML вместо JSON;
  `temp` отсутствует; `reportTime` отсутствует или мусор; миллисекунды в
  `reportTime` разбираются; `temp` вне диапазона отбрасывается.
- Свежесть: устаревшая сводка отброшена при 2400 с; протухшая не попадает в
  словари.
- Бакет: METAR попадает в час наблюдения, а не час прогона.
- Сбой METAR не обнуляет MQTT-станции.
- `stations.json`: 6 станций, из них одна `metar`; у всех только
  `temperature_2m`.
- `load_stations`: принимает `source: "metar"`, отвергает неизвестный;
  `max_age_s` не число или не положительное — отвергает.
- Дубликаты: фиксирует известное ограничение (документационный тест).

Переписываются тесты, закрепляющие старое состояние:

- `test_sensors.py:1042-1052` — «5 станций, ровно одна с `source: http`».
- `test_sensors.py:227-235` — валидность конфига (остаётся верным, но надо
  убедиться, что не проверяет число станций).
