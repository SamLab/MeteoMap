# Температура датчика в виджете с направленным округлением

Дата: 2026-09-30
Статус: утверждён к реализации

## Задача

Строка виджета (`meteo.html`, `meteow.html`) сейчас несёт только сводку по дождю:

```
🌤 Небольшая морось Пн 5 16ч—19ч [0мм_13%] 3-4м
```

Температуры датчиков в ней нет: виджет показывает её отдельной строкой «Датчик» в
таблице, а в самом виджете — только прогнозные значения в часовой ленте.

Требуется вынести температуру датчика в строку виджета:

```
🌤 +5 Небольшая морось Пн 5 16ч—19ч [0мм_13%] 3-4м
```

Одновременно вводится правило округления до целых: при активном солнце — в
большую сторону, ночью (от заката до рассвета) — в меньшую.

## Решение

### Что показываем

Берётся **последнее наблюдение датчиков**, а не прогноз:

- источник — `models.sensors.temperature_2m`;
- час ищется назад от текущего (`idx`), как в `lastSensorHour()` главной страницы;
- берётся среднее по станциям, а для Цеденево ночью — минимум
  (`sensor_station_min`), то есть ровно то же значение, что показывает строка
  «Датчик» главной страницы. Иначе виджет и страница расходились бы в цифре
  рядом с общим заголовком.

Виджет сам получает полный payload того же города, поэтому все нужные поля
(`sensor_station_counts`, `models.sensors`, `sensor_station_min`, `daily`) уже
доступны — запрос данных менять не нужно.

### Правило округления

| Условие | Округление | Пример |
|---|---|---|
| День: рассвет ≤ час < закат | `Math.ceil` | 5.2 → 6 |
| Ночь: закат ≤ час, час < рассвет | `Math.floor` | 5.8 → 5 |

Обоснование: днём округление вверх показывает более тёплую оценку, ночью — более
холодную. Ночная оценка важнее для решения «укрываться или нет», поэтому она не
сглаживается вверх.

Знак: `+5` для положительных, `-3` для отрицательных, ноль без знака — как в
существующей часовой ленте виджета.

Границы взяты из `daily.sunrise`/`daily.sunset` того же дня, к которому относится
час. Час, начинающийся до рассвета, — ещё ночь; час, не переваливший закат, — ещё
день. Те же границы, что у `sensorIsDayAt()` главной страницы: виджет и страница
не должны расходиться в том, считается ли час ночным.

### Значение при отсутствии данных

Если датчиков нет (города без станций, пустой текущий час) — строка виджета
остаётся прежней, без температуры. Это осознанный дефолт: в строке заголовка
нет места для прочерка, а пустой префикс дешевле, чем «—» перед сводкой.

### Формат

```
🌤 +5 Небольшая морось Пн 5 16ч—19ч [0мм_13%] 3-4м
```

Знак градуса не ставится: целое число в заголовке виджета читается как значение,
а не как замер с единицами; часы ленты показывают градусы, заголовок — нет.

Разделитель между температурой и сводкой ставится **только если префикс есть**:
`sensorTemp ? sensorTemp + ' ' : ''`. Безусловный пробел дал бы в городах без
станций два пробела подряд, а склейка без пробела — «+14Дождь». `buildSummary()`
не возвращает ведущих пробелов ни в одной ветке, и `widgetSensorTemp()` не
добавляет хвостовых, поэтому разделитель обязан быть явным.

### Где именно

Обе строки сборки виджетов (`meteo.html`, `meteow.html`) уже обязаны держать
одинаковые формулировки — это проверяет `test_widget_summary_formats_match_both_widgets`.
Новая функция добавляется в оба файла симметрично.

## Отклонения и границы

- Часовая лента виджета не меняется: там прогноз, а не наблюдение, и он уже
  округляется обычным `Math.round`.
- Главная страница не меняется: строка «Датчик» остаётся с десятичной точкой и
  временем замера — там нужна точность, в заголовке виджета — целое.
- Правило округления применяется только к температуре датчика в виджете.

## Проверка

Структурные тесты на оба файла виджетов (как принято в `tests/test_radar.py`)
плюс воспроизведение округления на Python для контроля границ и отрицательных
значений: `ceil` днём, `floor` ночью, ровные значения не меняются, `13.18` → `14`
днём и `13` ночью.
