# Датчики как источник погоды: столбик «Датчик» в «Часах»

Дата: 2026-09-28
Статус: утверждён
Заменяет: слой датчиков на карте Радара (спека `2026-09-28-sensors-on-radar-map-design.md`)

## Цель

Собрать все метеостанции с MQTT-брокера `yar.gorod76.ru` в один новый источник
погоды по имени «Датчик» и показать его отдельным столбиком во вкладке «Часы»
для Ярославля и Цеденево. Значение столбика — среднее по станциям отдельно для
каждого параметра. Слой датчиков с карты Радара удаляется полностью.

## Контекст, который определяет решение

Вкладка «Часы» — не сводка текущей погоды. Это сетка из 384 строк (16 суток ×
24 часа) и колонок-источников. Все источники хранятся в `data/<slug>.json` как
`models[code][var]`, массивы длиной 384, выровненные по `time[]`. Ось времени —
локальное время `Europe/Moscow` в формате `%Y-%m-%dT%H:00`
(`meteo.py:16`, `align_to_grid` в `meteo.py:434`).

Датчики физически не выдают прогноз — только текущее измерение. Из девяти
стандартных параметров приложения они закрывают три. Это ключевое ограничение,
определяющее всю конструкцию: столбик заполняется только для прошедших часов.

## Решения

| Вопрос | Решение |
|---|---|
| Ось времени столбика | Только прошедшие часы; будущие — `—` |
| Правило усреднения | Одно значение параметра на станцию, затем среднее по станциям |
| Роль в таблице | Полноценный участник консенсуса |
| Вес в консенсусе | Двойной относительно каждой модели |
| Где живёт история | Коллектор копит и коммитит, `meteo.py` читает |
| Города | Только `yaroslavl` и `tsedenevo` |

### Почему одно значение на станцию

Температуру публикуют 9 станций и 20 каналов. Из них `city/out/temp_min` —
городской агрегат, а `frunze/temp_min` и `penaty/tempavg` — производные значения,
так что физических датчиков температуры 18. Каналы неравнозначны:

- **Ярбатут** — три канала с одного места: `dstmp4_0` 20.4, `dstmp4_1` 20.9,
  `dstmp5_0` **28.9** (на 8 °C теплее остальных — другой датчик);
- **Фрунзе** — `temp/left` 14.99 и `temp/right` 20.3, плюс `temp_min` 14.99,
  который не датчик, а производное значение `min(left, right)`;
- **Запад** — `city/in/west/temp/ds` 16.06 это **в помещении**,
  `city/out/west/temp/ds` 18.62 снаружи;
- **Пенаты** — `tempavg` 16.25 и `humavg` 87.81 тоже производные;
- **ESPHome** — по два канала на устройство (свой SHT и BME280).

Усреднение по каналам дало бы Ярбатуту тройной вес, учло бы производные
значения второй раз и смешало уличную температуру с комнатной. Поэтому схема
конфига становится строгой: одна станция — одно значение на параметр.

Выбор конкретного канала по каждой станции вынесен в отдельный проход
(см. «Отложенные вопросы»), но код не должен позволять вернуться к нескольким
каналам на параметр.

## Архитектура

```
sensors.yml  (cron */15, отдельный workflow)
    └─ tools/collect_sensors.py
         ├─ читает stations.json (строгая схема: 1 топик на параметр)
         ├─ слушает живой эфир window_s секунд, retained игнорирует
         ├─ валидирует значения по диапазонам
         ├─ среднее по станциям на каждый параметр
         ├─ дописывает per-station значения в sensors_history.json (бакет часа)
         └─ пишет sensors.json (текущий снимок, для диагностики)
              ↓ оба файла коммитятся в репозиторий

deploy.yml  (cron 0 * * * *, отдельный workflow)
    └─ meteo.py
         ├─ читает sensors_history.json
         ├─ для slug yaroslavl / tsedenevo строит models["sensors"]
         ├─ добавляет sensors в model_codes, "Датчик" в model_names
         ├─ назначает вес и пересчитывает консенсус
         └─ остальные 7 городов не затрагивает
```

Коллектор владеет историей, а `meteo.py` остаётся без состояния. Причина: `data/`
в `.gitignore`, а CI стартует с чистого checkout, поэтому накопление внутри
`meteo.py` без внешнего кэша или коммита обнулялось бы на каждом прогоне. Отдельный
коммит раз в 15 минут — единственный способ сохранить историю и не потерять
cadence.

## Конфиг станций

`tools/stations.json` переезжает на схему с каноническими именами переменных
`meteo.py`, чтобы у коллектора и `meteo.py` не было таблицы перевода:

```json
{
  "broker": "yar.gorod76.ru",
  "port": 1883,
  "window_s": 240,
  "history_days": 30,
  "stations": [
    {
      "id": "yarbatut",
      "name": "Ярбатут",
      "lat": 57.64033,
      "lon": 39.88513,
      "sensors": {
        "temperature_2m": "/yarbatut/2054001-1458270/dstmp4_0/status"
      }
    }
  ]
}
```

Значение — строка-топик, а не пара `[kind, topic]`: вид параметра однозначен по
имени, поэтому отдельный `kind` избыточен.

### Разрешённые параметры

Валидация конфига принимает **только** три параметра:

- `temperature_2m` — диапазон −50…50
- `relative_humidity_2m` — диапазон 0…100, значения ≥99.5 считаются заглушкой
- `pressure_msl` — диапазон 600…820

Любой другой ключ отклоняется с сообщением о том, что такой датчик в сети не
измеряется. Это защищает от попытки замапить в колонку «Датчик» ветер из
мёртвой `yarecologia` или `temp_min`, который является производным значением.
Совпадение с именами переменных в `CHART_VARS` (`template.html:288`) позволяет
подставлять значения в таблицу без преобразований.

Снято живьём 28.09.2026, окно 240 с. Отмеченные `pending_review` — кандидаты на

Не используются и исключены по построению: `dstmp5_0` (Ярбатут, 28.9),

### Покрытие неравномерно, и это видно в данных

- температура — 6 станций;
- влажность — 4 станции (нет у Ярбатута, Запада);
- давление — 2 станции (Фрунзе и Восток, обе в южной части города).

Среднее по двум станциям в одной части города — это не «среднее по Ярославлю».
Столбик давления показывает локальную точку, и его нельзя читать как городскую
величину. Число участников пишется в историю рядом со значением.

## Усреднение

`average[param] = mean(значений станций)`. Станция, не ответившая за окно,
**исключается**, а не считается нулём. В `sensors.json` пишется число
участников и их список, чтобы по снимку читалось `3/6`.

Ранжирования станций нет: все равноправны.

## История

`sensors_history.json` в корне репозитория, коммитится `sensors.yml`.

```json
{
  "hours": {
    "2026-09-28T12:00": {
      "samples": 4,
      "stations": {
        "yarbatut": {"temperature_2m": [20.4, 20.5, 20.6, 20.4]},
        "frunze":  {"temperature_2m": [14.9, 15.0],
                    "relative_humidity_2m": [92.3, 92.1],
                    "pressure_msl": [765.4]}
      }
    }
  }
}
```

Ключ часа — локальное московское время, совпадающее с элементом `time[]`, поэтому
сопоставление прямое, без конвертации.

Значение часа считается как `mean` по станциям от `mean` по замерам этой станции.
Каждая станция весит одинаково независимо от того, сколько прогонов её видели.
Схема со списками по станциям выбрана именно поэтому: усреднение по прогонам
дало бы одинокая станция с одним замером тот же вес, что и шесть станций с
четырьмя.

`samples` — число прогонов в часе. Хвост старше `history_days` (30) обрезается.
Если за окно не ответила ни одна станция, бакет **не пишется вовсе**: пустое
среднее в истории хуже отсутствия записи.

## Инъекция в `meteo.py`

Выполняется после `assemble_consensus` (`meteo.py:1221`) и только для
`slug` из списка `SENSOR_LOCATIONS = {"yaroslavl", "tsedenevo"}`.

1. Читается `sensors_history.json`. Отсутствующий или нечитаемый файл — не ошибка:
   выводится предупреждение, столбик не добавляется, сборка продолжается как
   раньше.
2. Для каждой из трёх переменных строится массив длины `len(time)`. Часы, есть
   которые в истории, заполняются средним; остальные — `null`.
3. `sensors` добавляется в `model_codes`, в `model_names` кладётся `"Датчик"`.
4. Назначается вес и пересчитывается консенсус (см. следующий раздел).
5. В `verification` датчики не участвуют: там нужны исторические прогнозы, а у
   нас наблюдения. Вклад наблюдения в проверку точности исказил бы MAE-модель,
   по которой `make_weights` (`meteo.py:1048`) сам же строит веса.

Остальные семь городов (`rybinsk`, `rostov`, `petropavlovka`, `moscow`, `loo`,
`borok`, `batumi`) не затрагиваются. Столбик появляется только там, где в
`model_codes` есть `sensors`.

## Вес в консенсусе

Веса в `weighted_consensus` (`meteo.py:1095`) используются только как
**отношения**: значение делится на сумму весов присутствующих источников.
Поэтому нормировка на единицу не нужна и не влияет на результат, а «двойной
вес» задаётся относительно среднего веса модели:

```
w_sensors = 2 × mean(веса остальных моделей по этой переменной)
```

Остальные модели не трогаются, сумма весов после добавления не равна 1 — это
неважно, так как важны только пропорции.

При `N = 12` моделях с равными весами: `w_sensors = 2`, каждая модель `1`,
доля датчиков `2/14 ≈ 14.3 %`, ровно вдвое больше доли любой модели.

### Важная тонкость: у двух параметров весов нет

`VERIFICATION_VARIABLES` (`meteo.py`) содержит только
`['temperature_2m', 'precipitation', 'wind_speed_10m']`. Для
`relative_humidity_2m` и `pressure_msl` записи в `weights_by_var` отсутствуют,
и `assemble_consensus` подставляет всем моделям `fallback = 1.0` — то есть
считает их **обычным средним**, а не точным консенсусом.

Поэтому для этих двух переменных нельзя просто взять `2 × mean(...)` от
`weights_by_var`: там лежит пустой словарь, `mean` даст 0, и вес датчика станет
нулевым либо, при добавлении записи по умолчанию, сравняется с весом одной
модели вместо двойного. Правило:

- переменная есть в `weights_by_var` → `w_sensors = 2 × mean(веса моделей)`,
  веса моделей сохраняются как есть;
- переменной нет в `weights_by_var` → моделям явно ставится `1.0` каждая
  (это ровно то, что делает текущий `fallback`), датчику `2.0`.

Оба случая дают датчику вдвое больше веса, чем любой отдельной модели, и
ни один вес модели не меняется относительно текущего поведения.

Консенсус пересчитывается только там, где у датчиков есть значение.
`weighted_consensus` (`meteo.py:1095`) уже отбрасывает `None`, поэтому будущие
часы не меняются ни на единицу: сдвиг возможен исключительно в прошедших часах,
где наблюдение заменяет архивный прогноз.

Известное следствие, осознанно принятое: колонка «Среднее» по этим трём
параметрам в прошедших часах сместится в сторону фактического наблюдения. Для
давления это смещение опирается всего на две станции.

## Интерфейс «Часов»

Заголовок «Датчик» берётся из `model_names`, правки разметки не требуется.

`cmpColOrder(codes)` (`template.html:1098`) вызывается в трёх местах: наборы
данных графика (`:987`), легенда (`:1082`) и таблица сравнения (`:1110`).
Значит «Датчик» появится ещё и линией на графике. Это оставляется: линия
показывает наблюдения там, где графики моделей показывают их же прогнозы, и
`spanGaps:false` обрывает её на текущем часе, так что продолжения читать
не приходится.

Добавляется фильтр по переменной: «Датчик» показывается только для
`temperature_2m`, `relative_humidity_2m`, `pressure_msl`. При выборе ветра,
осадков, облачности, CAPE или WMO столбик отсутствует целиком, а не рисуется
пустым серым.

## Тесты

Раскладка по существующим файлам, без создания новых.

`tests/test_sensors.py` — коллектор:

- конфиг отклоняет два топика на один параметр;
- конфиг отклоняет параметр вне белого списка;
- среднее не учитывает станции без живых значений;
- в снимок пишется число участников и их список;
- повторный прогон в том же часе дописывает, новый час создаёт бакет;
- значение часа — среднее по станциям от средних по замерам, станция с одним
  замером не получает вес шести;
- хвост старше `history_days` обрезается;
- при нуле ответивших станций бакет не пишется.

`tests/test_weights.py` — веса:

- `w_sensors` ровно вдвое больше среднего веса модели по каждой из трёх
  переменных;
- для `relative_humidity_2m` и `pressure_msl`, которых нет в `weights_by_var`,
  модели получают `1.0` каждая, то есть как при текущем `fallback`;
- ни один вес существующей модели не меняется относительно текущего поведения.

`tests/test_consensus.py` — консенсус:

- консенсус в часах, где у датчиков нет данных, не изменяется;
- в часах с данными датчиков консенсус пересчитывается;
- `None` от датчика не ломает расчёт и не считается нулём.

`tests/test_locations.py` — область применения:

- `sensors` появляется в `model_codes` для `yaroslavl` и `tsedenevo`;
- для остальных семи слагов `sensors` в `model_codes` отсутствует.

`tests/test_generation.py` — форма вывода:

- длины массивов `models["sensors"][var]` равны `len(time)`;
- ровно три переменные;
- часы без истории дают `null`, а не 0.

`tests/test_render.py` — интерфейс:

- заголовок «Датчик» рендерится при наличии кода в `model_names`;
- набор данных «Датчик» отфильтровывается для неизмеряемых переменных.

Отсутствующий или битый `sensors_history.json` не роняет сборку — тест на это
идёт в `tests/test_locations.py`.

Интеграционная проверка: полный набор тестов зелёный плюс один реальный прогон
коллектора, дающий валидные `sensors.json` и `sensors_history.json`.

## Отложенные вопросы

По условию пользователя каналы по станциям будут пересмотрены отдельным
проходом. Подготовлены, но не решаются сейчас:

- **Ярбатут**: `dstmp5_0` = 28.9 против 20.4 и 20.9 у соседних каналов. Если это
  не ошибка датчика, а нагретый участок, усреднение по трём каналам было бы
  честнее, чем один.
- **Фрунзе**: разброс `temp/left` 14.99 и `temp/right` 20.3 — 5.3 °C. Влажность
  расходится ещё сильнее: `hum/left` 92.33 против `hum/rigt` 50.93. Какая
  сторона улицы представляет район — вопрос к владельцу датчиков.
- **Восток**: `temp/ds` 15.31 против `temp/bme` 21.43 — 6 °C.
- **Берег**: `dstmp17` 15.3 против `tmp315` 14.30.
- **Пенаты**: `temp` 16.2 против `temp/ws01` 16.25 — расхождение несущественное,
  выбор не критичен.
- **Берег-2** (`/dbereg_2/5438543-1458270/tmpwifi1` = 23.94) сейчас присоединён к
  Берегу вторым каналом температуры. В новой схеме это либо отдельная станция,
  либо не учитывается. Решение требует координат.
- **Две живые ESPHome-станции** `weather-station-c472ac` (19.7 °C, 41.4 %,
  763.2 мм) и `weather-station-e06536` (15.4 °C, 49.2 %, 766.0 мм) не включены
  ни в одну из шести станций. У `e06536` топик `status` содержит `offline`, хотя
  сенсоры публикуются в эфир; при включении нельзя ориентироваться на `status`.

## Чего сознательно не делаем

- Не добавляем ветер, осадки, вероятность осадков, облачность, CAPE и WMO-код:
  датчики их не измеряют. Подставлять туда внешние API значило бы выдавать
